## Objective and T2 boundary

ExpertAI should help users discover suitable HEDGE-IoT Store Apps, understand their
documented capabilities and compare options through natural conversation. English
is the current priority; Turkish refinement is deferred.

The tracked [proposal](proposals/HEDGE-IoT-OC1-Proposal-HedgeExpertAI.md), Task 2,
commits to a Rasa + LLM conversational core, source-grounded responses, automatic
Store ingestion/indexing, hybrid discovery/ranking with optional SAREF signals,
initial sandbox/API/frontend connectivity, and tested containerized services with
prototype CI/monitoring. Later T3/T4 integration, pilot validation and final release
are separate. Small authored evaluations do not establish the proposal's jointly
labelled sandbox relevance, latency, freshness or recommendation-acceptance KPIs.

For the private Store path, inspected code executes:

1. Angular → gateway → `run_chat_v2()` in chat routes. Rasa supplies intent/entities;
   application code owns operation precedence, reference binding and constraints.
2. `chat-intent/app/private_store.py` binds the policy to Expert and Discovery HTTP
   endpoints. Prepared browsing, metadata reads, references and supported requests
   can complete without inference. Valkey sessions retain context/history.
3. Uncertain ordinary English requests, when enabled, use one structured Ollama
   interpretation: operation, conversational reference, one source-function key
   and unmatched requirements. Its bounded menu contains automatically prepared
   functions admitted by the same source assessor. The model does not grant
   suitability or write ordinary-path factual prose. Legacy/deep-reasoning paths
   also exist; flags and entry points matter.
4. Expert requests Discovery `/api/v2/apps/search`. PostgreSQL lexical retrieval
   uses an OR pool and the English dictionary for English Store requests; other
   locales retain `simple`. E5 query/passage embeddings search Qdrant. Default RRF
   weights are dense .55 / lexical .45, K=60. Five-result requests use a 40-candidate
   channel budget; raw scores are not comparable confidence values.
5. Candidate references are hydrated against current PostgreSQL Store membership,
   publication, revision and filters. `assess()` and `_recommendation_decision()`
   separate supported recommendations from unverified candidates. Interpreted
   requests can trigger retrieval again; strict restrictions retain original text.
6. Expert's prepared presenter composes source-backed text. Chat rechecks current
   catalogue data before returning results/SSE and updating context. Retrieval rank
   alone never grants support.

Separately, ingestion uses Keycloak M2M credentials from secure configuration,
reconciles the durable PostgreSQL projection/outbox, automatically prepares English
knowledge, and repairs derived Qdrant state. Identity is native Store ID + App ID.
ExpertAI `/api/v2` is distinct from HEDGE Store `/api/v1`; the rich synthetic v2
fixture contract must not be imposed on sparse real Store records.

## Evidence and current limitations

Demonstrated work includes authenticated synchronization of two authorized Apps,
incremental indexing, automatic extractive English preparation, real-service/widget
conversations, prepared metadata/reference flows, and the approved Angular UI.
This does not demonstrate a custom-trained expert model or general English quality.

The last ranking study used 20 authored Apps (19 eligible), 24 development queries
and eight held-out queries. Final hybrid positive-query HitRate@2 was 100%; frozen
Recall@5 was 98.75%. Frozen MRR regressed .900 → .875 while holdout MRR improved
.833 → 1.000. Partial fits can outrank complete fits; one broad-query alternative
remains outside five. This is controlled engineering evidence, not a live Store KPI.

The latest 12-request recommendation assessment found relevant Apps in the top two
for all eight positive requests, but prepared final decisions remained **4 Pass /
0 Partial / 8 Fail**, before and after. All eight positives abstained; the four
unsupported cases were declined. Three completed final Qwen-assisted cases scored
**1 Pass / 0 Partial / 2 Fail**, with two false abstentions and no unsupported
recommendations observed. Two baseline calls were unassessed after a recorder
dependency failure; they were not counted as product failures or replayed.

`4f397ed` repairs source-proof ownership/neutral-context rejection and separates an
App's grammatical name from its functional task query. It blocks an imperative-based
proof approval. It does **not** close natural recommendation quality: Qwen still
ignored an admissible aggregation task, and a compound request retained its three
requirements without receiving complete admissible support. Adjacent qualifications,
bounded claim grammar, one-function normalization and interpretation reliability
remain limitations. Earlier NLU/context records also contain wrong operations,
wrong references and false negative source claims. No global no-regression claim
or T2 recommendation acceptance follows from passing unit tests.

Latest recorded verification: 1,367 unit tests passed, shared branch coverage
88.14%, and 151 focused checks passed after final normalization review. No expensive
tests or new inference were run to prepare this documentation handoff.
