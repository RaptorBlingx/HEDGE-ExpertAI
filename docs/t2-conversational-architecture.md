# T2 conversational architecture (22 October 2026)

Branch `feat/t2-conversational-architecture`, based on the deployed `86fa782`.
This replaces the Store dialogue policy. The knowledge layer (App guides,
glossary, explainer), the evidence verifier and the native-identity and
revision safeguards are kept. Results and their limits are in
[Evaluation](#evaluation); the decision record is in [Decisions](#decisions).

## Why the previous design failed ordinary questions

Investigation of the owner's 8156 session (diagnosis, 22 October) found:

- **Language understanding was hand-written.** About 270 regular expressions in
  seven modules (`store_dialogue.py`, `store_conversation.py`,
  `conversation_acts.py`, `store_language.py` grammars, the Expert presenter)
  decided what a message meant. Several layers re-interpreted the same turn;
  about 15 rules rewrote the planner's output. 27 commits since September
  patched individual phrasings.
- **Anything unparsed became a capability search**, with the whole message as the
  requirement ("Tell me about Edge-Connect" was "verified" against the readme).
- **The model fallback could not run on 8156.** Planner prompts of 680–820 tokens
  against ~7 tokens/s prompt processing timed out at 90 s on every call.
- **App names matched exactly**, so "Edge Connect" did not name "EdgeConnect".
- **Rasa's intent was discarded** by the routing grammar.

## Architecture

```
message + dialogue state
  └─ Interpreter (chat-intent/app/understanding.py) — one Frame per turn
       ├─ AppLinker (hedge_shared/app_linker.py): names however spelled, source
       │  aliases, providers, exact native IDs; ambiguity is reported, not guessed
       ├─ references: closed-class pronouns, ordinals, "the other one", "both",
       │  resolved against what was shown, focused, compared or discussed
       ├─ act: Rasa DIET + E5 nearest examples, both over dialogue_acts.json with
       │  App mentions masked; agreement accepts, disagreement → model choice
       │  (STORE_SEMANTIC_ENABLED) → else one plain question to the user
       └─ structure: an act's slots (subject, need) from the message and state;
          words beyond the acts' own vocabulary are a functional need
  └─ Assistant (chat-intent/app/assistant.py) — executes the Frame, owns the state
       ├─ list → current catalogue        ├─ describe/simple/example/how/… → explainer
       ├─ provider/price/access/details → source fields (answers.py)
       ├─ check/choose → verifier (+ model review of paraphrases, when enabled)
       ├─ find → Discovery retrieval + verifier (+ review)
       ├─ ask → explainer: one cited model answer, else quoted statements
       └─ clarify, small talk, dropping a condition
```

**Ownership.** The interpreter alone decides intent and identity; executors never
re-read the wording. The assistant alone owns the dialogue state, stored under
`context["dialogue"]`: `shown`, `focus`, `compared`, `discussed`, `need`, `last`
(act, subjects, need), `pending_filters`, `explanations`. Recommendations come
only from the verifier's decision, as before.

**Acts.** 26 dialogue acts with plain-English glosses and English examples live in
`shared/hedge_shared/dialogue_acts.json`. App mentions are written `APP`, so the
examples hold for any future App. Need acts mark the requested function with
Rasa's entity markup (`is there an app for [settlement](need)`); the words around
those spans, with the needless acts' examples, are the vocabulary of *asking*.
Anything else in a message is a functional need. This turns "Can X forecast
solar?" into a check rather than a description, and "list apps for meters" into a
search rather than a listing, without phrase rules.

**Rasa's role.** The proposal commits to Rasa for intent classification and
entity extraction. Rasa now classifies the assistant's acts from the shared
corpus (`hedge-expertai-nlu-v3`, generated by `scripts/generate_rasa_nlu.py`) and
learns the need entity. It is one of two independent signals: measured on
development turns, Rasa and E5 each reached about 90% alone and failed on
different utterances; where they agreed they were almost always right. Readings
below `RASA_CONFIDENCE_THRESHOLD` are ignored.

**Model use.** On this hardware (2 vCPUs, ~7 tokens/s prompt processing on 8156),
the model cannot read every turn. It is used where nothing else can decide: a
choice between two readings (a ~100-token prompt with fixed instructions first,
`STORE_INTERPRETATION_SECONDS`), reviewing whether an App's own sentences state a
paraphrased need (`review.py`, into the existing `ReviewedSupport` receipt), and
open questions (`explainer.open_answer`, unchanged). Without the model every turn
still gets an answer: a clarification, the closest unconfirmed statements, or the
statements that bear on the question.

## Safeguards kept

- Native identity: exact, case-sensitive IDs; shared names are ambiguous; a
  clicked card answers about its own App or says it is unavailable.
- Every shown App is resolved from the current catalogue and checked again after
  slow steps; streamed text is released only while its Apps are unchanged.
- Recommendations only from the verifier; a review cannot handle quantities,
  absences, conditions or limitations, and its receipt is bound to the request,
  the App and its source digest.
- Pricing conditions and typed catalogue filters are unverifiable: they stay
  pending and are shown as such until dropped. One gate after execution holds
  back every recommendation while one is pending, whichever path produced it
  (search, capability check, choice, model review).
- Need normalization never removes words carrying polarity, conditions or
  exclusions ("not", "never", "without", "only", "if", "instead of").
- The verifier credits an App only with what it does or provides, not with what
  it works from ("from weather data", "against price forecasts supplied by the
  user"); a requirement's own inputs may match the App's inputs, and an interface
  it reads from ("from MQTT devices") counts as supported. Sentences led by
  people or other products are not the App's claims; a requested absence
  ("without internet access") needs a stated one; a stated absence answers "no"
  only when it concerns the request.
- Model review takes only the App's own claims, never an App whose source
  delegates the function to another product or people, never a sentence related
  to the need only through its inputs, and never quantities, absences or
  conditions.
- Model text is still released sentence by sentence through the existing checks.

## Decisions

| Decision | Why | Rejected alternative |
| --- | --- | --- |
| Statistical act classification over one labelled dataset, App mentions masked | Generalizes to paraphrases and future Apps; one place to extend | More grammars (the failed approach); model-first (cannot run per turn here) |
| Two classifiers, agreement as confidence | Measured complementary errors; Rasa is a project commitment | Rasa alone (weaker on paraphrase); E5 alone (weaker on some structures) |
| Deterministic linker and references | Names and pronouns are identity, not semantics; must be exact and auditable | Letting a model pick Apps |
| Model only for disagreements, paraphrase review, open questions | Fits measured CPU throughput; every path has a model-free answer | A per-turn planner (timed out on every call) |
| One typed state under `dialogue` | Replaces a dozen loose keys and raw-string "needs" | Keeping legacy keys |
| Remove StoreConversation/StoreDialogue/act grammar, `/interpret`, `/reason`, `store_answers` | One owner per concern; dead paths invite patches | Leaving them as fallbacks |

**Protocol and its limits.** All sets were written before implementation and
committed first (`1d160da`); the held-out sets were run at milestones and their
failures informed general changes, each recorded in the commit messages; the
final set and its unseen-App catalogue were run once per configuration, after the
code was frozen. Training examples are checked for overlap with sealed messages
(`leakage.py`). The same author wrote the sets and the code, and the sets are
small (110 turns), so these are engineering measurements, not acceptance.

**What the runs found and changed.** The integrated stack found a startup crash
(an API missing in the deployed FastAPI), a model-review false positive (an API
sentence approved as "data mapping"; reviews beyond the verifier's nominations
now also need E5 relevance at the verifier's own floor), and implicit-focus and
pronoun gaps; the integration suite found that unconfirmed candidates were being
sent as recommendation cards (and impressions), and stale-reference handling.
A rule that offered both E5 readings on a near-tie was tried and reverted after
it made answers worse.

**Recommendation decisions** (`evaluation/recommendation`, single requests through
the whole assistant, E5 only): identical to `86fa782` on `unseen.json` (10 Pass,
13 Suggested, 1 Fail) and on `unseen-2.json` except one case that improved from
Fail to Suggested; no recommended set changed. A first run found three requests
misread without Rasa (a bare keyword and an imperative read as term questions, a
need with no App asked "which App?"); two structural rules fixed them (a message
of function words and no App is a search; a need with no App to be about is a
search). They followed the final run, so a post-hoc offline rerun of every set
was made: results unchanged.

Other verification: Ruff clean; 1,285 unit tests; integration suite against
disposable PostgreSQL/Qdrant/Valkey 3 failures, all inherited from `86fa782`
(27 failures there, 24 of them in tests of removed code).

## Corrections after independent review (22 October)

An independent review (Codex) blocked deployment on three defects, each now
reproduced by tests that fail on `912b347` and pass after the fix:

| Defect | Root cause | Correction |
| --- | --- | --- |
| Negation reversed ("must not collect personal data" recommended the App that collects it) | Trimming the request's leading words removed "must not"; review's negation guard then saw none | Trimming stops at polarity, condition and exclusion words; "instead of" survives |
| Unresolved conditions bypassed | A search checked pending conditions before model review, which could then promote an App | One gate after execution for every path |
| Inputs taken for capabilities (inherited from `86fa782`) | The verifier matched requested words anywhere in a sentence | Sentences and requirements are split into what is done and what is worked from; review never reconsiders input-only matches |

Driving the corrections through live and integrated runs found more of the same
class, also fixed: "Field engineers inspect substations" credited to the App
(inherited); a requested absence that could never match a stated one
(inherited); model review approving a sentence about people, or an App whose
source says another application does the work; the input guard missing
paraphrased needs; review spending its budget on non-reviewable candidates; a
negated sentence nominated by similarity alone answering "no"; a fallback
reading outranking a direct one. A review-prompt addition about inputs made the
model reject a correct paraphrase and was reverted; deterministic guards carry
that rule.

**Scorer.** Every recommendation must be anticipated by the turn (an exact
`recommend` set, or the Apps it expects); an extra one fails the turn even beside
the expected App. Rescoring earlier runs with this rule exposed recommendations
the old scorer passed: LoadAhead for "meter data", VPP Studio for "forecasts
solar", EdgeConnect for "map data between two systems".

**Safety set.** `safety.json` over `catalogue-safety.json` (17 turns, exact
recommendation sets) covers negation, conditions, actor ownership, inputs
versus outputs and a pricing condition across search, check, choice and review.

## Limitations

- **Classifier coverage is data.** Some ordinary phrasings are still misread
  ("Who runs it?", "What can I find in here?"), and domain words inside training
  examples bias acts: "what's OpenADR?" was read as a capability check because a
  check example mentions OpenADR. More varied examples (with need spans marked)
  are the remedy, not rules; a held-out review of the dataset is advisable.
- **Asking vocabulary is learned from the examples**, so casual words it has not
  seen can count as a need: "what's the hedge store got?" became a search.
- **Paraphrased capabilities need the model.** Offline, the lexical verifier
  hedges ("EV chargers" does not match "electric vehicle chargers"). Model review
  false positives found so far are fixed by deterministic guards, and the
  remaining decision rests on a 4B model. Its precision has not been measured at
  scale; it is the main recommendation-safety risk to review independently.
- **Role and ownership detection is grammatical**, not parsed: input phrases
  start at a closed set of prepositions and end at clause boundaries, verbs or
  coordinated predicates; actors are recognised at sentence start. Phrasing it
  does not recognise is verified as before this correction, so an input or a
  delegated function written unusually can still be credited to an App.
- **The 4B model embellishes** open answers ("this payment comes from the local
  system operator"); sentence checks are not entailment.
- **Latency** of model turns (15–77 s) was measured on an isolated copy with
  8156's limits; 8156 itself may be slower under contention. The model's memory
  sizing is unchanged and still to be reviewed.
- **Access links** (UI, OpenAPI, deploy URLs) are in the Store record but not in
  the recommendation projection, so "where is its API documentation?" is not
  answered; adding them needs a preparation-version bump.
- **Not supported:** provider-scoped follow-ups ("do they have anything else?").
- **Languages.** E5 and Rasa's templates are multilingual, but answers are
  English source text; the earlier Turkish dialogue grammar was removed with the
  rest and Turkish was not re-evaluated.
- **Not done:** the approved Angular widget was not re-driven in a browser (the
  API and SSE contract are unchanged and were exercised through the gateway); no
  real-user session; no multi-user load.
