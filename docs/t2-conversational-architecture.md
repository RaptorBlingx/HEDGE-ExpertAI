# T2 conversational architecture (22 October 2026)

Branch `feat/t2-conversational-architecture`, based on the deployed `86fa782`.
This replaces the Store dialogue policy. The knowledge layer (App guides,
glossary, explainer), the evidence verifier and the native-identity and
revision safeguards are kept. Results and their limits are in
[Evaluation](#evaluation); the decision record is in [Decisions](#decisions).

## Why the previous design failed ordinary questions

Investigation of the owner's 8156 session (diagnosis, 22 October) found:

- **Language understanding was hand-written.** About 270 regular expressions in
  seven modules (`store_dialogue.py`, `store_conversation.py`,
  `conversation_acts.py`, `store_language.py` grammars, the Expert presenter)
  decided what a message meant. Several layers re-interpreted the same turn;
  about 15 rules rewrote the planner's output. 27 commits since September
  patched individual phrasings.
- **Anything unparsed became a capability search**, with the whole message as the
  requirement ("Tell me about Edge-Connect" was "verified" against the readme).
- **The model fallback could not run on 8156.** Planner prompts of 680–820 tokens
  against ~7 tokens/s prompt processing timed out at 90 s on every call.
- **App names matched exactly**, so "Edge Connect" did not name "EdgeConnect".
- **Rasa's intent was discarded** by the routing grammar.

## Architecture

```
message + dialogue state
  └─ Interpreter (chat-intent/app/understanding.py) — one Frame per turn
       ├─ AppLinker (hedge_shared/app_linker.py): names however spelled, source
       │  aliases, providers, exact native IDs; ambiguity is reported, not guessed
       ├─ references: closed-class pronouns, ordinals, "the other one", "both",
       │  resolved against what was shown, focused, compared or discussed
       ├─ act: Rasa DIET + E5 nearest examples, both over dialogue_acts.json with
       │  App mentions masked; agreement accepts, disagreement → model choice
       │  (STORE_SEMANTIC_ENABLED) → else one plain question to the user
       └─ structure: an act's slots (subject, need) from the message and state;
          words beyond the acts' own vocabulary are a functional need
  └─ Assistant (chat-intent/app/assistant.py) — executes the Frame, owns the state
       ├─ list → current catalogue        ├─ describe/simple/example/how/… → explainer
       ├─ provider/price/access/details → source fields (answers.py)
       ├─ check/choose → verifier (+ model review of paraphrases, when enabled)
       ├─ find → Discovery retrieval + verifier (+ review)
       ├─ ask → explainer: one cited model answer, else quoted statements
       └─ clarify, small talk, dropping a condition
```

**Ownership.** The interpreter alone decides intent and identity; executors never
re-read the wording. The assistant alone owns the dialogue state, stored under
`context["dialogue"]`: `shown`, `focus`, `compared`, `discussed`, `need`, `last`
(act, subjects, need), `pending_filters`, `explanations`. Recommendations come
only from the verifier's decision, as before.

**Acts.** 26 dialogue acts with plain-English glosses and English examples live in
`shared/hedge_shared/dialogue_acts.json`. App mentions are written `APP`, so the
examples hold for any future App. Need acts mark the requested function with
Rasa's entity markup (`is there an app for [settlement](need)`); the words around
those spans, with the needless acts' examples, are the vocabulary of *asking*.
Anything else in a message is a functional need. This turns "Can X forecast
solar?" into a check rather than a description, and "list apps for meters" into a
search rather than a listing, without phrase rules.

**Rasa's role.** The proposal commits to Rasa for intent classification and
entity extraction. Rasa now classifies the assistant's acts from the shared
corpus (`hedge-expertai-nlu-v3`, generated by `scripts/generate_rasa_nlu.py`) and
learns the need entity. It is one of two independent signals: measured on
development turns, Rasa and E5 each reached about 90% alone and failed on
different utterances; where they agreed they were almost always right. Readings
below `RASA_CONFIDENCE_THRESHOLD` are ignored.

**Model use.** On this hardware (2 vCPUs, ~7 tokens/s prompt processing on 8156),
the model cannot read every turn. It is used where nothing else can decide: a
choice between two readings (a ~100-token prompt with fixed instructions first,
`STORE_INTERPRETATION_SECONDS`), reviewing whether an App's own sentences state a
paraphrased need (`review.py`, into the existing `ReviewedSupport` receipt), and
open questions (`explainer.open_answer`, unchanged). Without the model every turn
still gets an answer: a clarification, the closest unconfirmed statements, or the
statements that bear on the question.

## Safeguards kept

- Native identity: exact, case-sensitive IDs; shared names are ambiguous; a
  clicked card answers about its own App or says it is unavailable.
- Every shown App is resolved from the current catalogue and checked again after
  slow steps; streamed text is released only while its Apps are unchanged.
- Recommendations only from the verifier; a review cannot handle quantities,
  absences, conditions or limitations, and its receipt is bound to the request,
  the App and its source digest.
- Pricing conditions and typed catalogue filters are unverifiable: they stay
  pending, hold back recommendations and are shown as such until dropped.
- Model text is still released sentence by sentence through the existing checks.

## Decisions

| Decision | Why | Rejected alternative |
| --- | --- | --- |
| Statistical act classification over one labelled dataset, App mentions masked | Generalizes to paraphrases and future Apps; one place to extend | More grammars (the failed approach); model-first (cannot run per turn here) |
| Two classifiers, agreement as confidence | Measured complementary errors; Rasa is a project commitment | Rasa alone (weaker on paraphrase); E5 alone (weaker on some structures) |
| Deterministic linker and references | Names and pronouns are identity, not semantics; must be exact and auditable | Letting a model pick Apps |
| Model only for disagreements, paraphrase review, open questions | Fits measured CPU throughput; every path has a model-free answer | A per-turn planner (timed out on every call) |
| One typed state under `dialogue` | Replaces a dozen loose keys and raw-string "needs" | Keeping legacy keys |
| Remove StoreConversation/StoreDialogue/act grammar, `/interpret`, `/reason`, `store_answers` | One owner per concern; dead paths invite patches | Leaving them as fallbacks |
